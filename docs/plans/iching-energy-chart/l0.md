# L0 Strategic Outline — I-Ching Energy Chart Signal

**Scope:** L0 strategic outline only. No functional units, no file trees, no implementation
code. L1/L2 decomposition is deferred to a follow-up pass. DuckDB integration, the record-to-
aggregate bridge, test fixtures, and timestamp-unit resolution are explicitly out of scope here.

## 1. Objective Recap

The goal is a clean, pure-Rust I-Ching energy-chart calculator that derives a single **7-bit
signal** from an arbitrary Gregorian datetime (past or future) with no local file caching.
Bits 1–6 encode the hexagram binary index (0–63) using the little-endian bottom-to-top
convention defined in the research spec (§2.1). Bit 0 additionally must disambiguate moving-line
information for the Plum Blossom method (the only configured method that has moving lines); for
Gua Qi Sovereigns and Fu Xi Wheel, bit 0 must be constant zero.

The work splits into two modules: a pure, no-I/O calculation core under `src/ta/iching/` and a
Gangtionary external dependency under `src/ext/lunar/` that must be implemented **either** as a
pure algorithmic lunar-calendar conversion (preferred, since it is deterministic and network-free
and satisfies "no file caching") **or** as a free public API client. The offline fixture-based
adapter described in the research doc is explicitly rejected for this implementation. Focus in
this L0 plan is on Plum Blossom, which owns the only moving-line signal semantics; the Gua Qi and
Fu Xi methods are recognized but rank lower priority.

The research doc's full `IchingRecord` struct remains a valid *internal* shape but is **not** the
public signal interface. The public surface returns `u8` (7 bits used; top bit must remain zero for
future headroom).

## 2. Findings

- The layered architecture introduced in `7e97774` is verified present: `src/ta/` (kernel, ops,
  processor, error, prelude), `src/engine/`, `src/adapter/`, `src/query/`, `src/model/`,
  `src/ext/`, and `src/time_utils/`. `src/ta/README.md` and `src/ext/README.md` document that
  `ta` and `ext` each depend only on `model` and neither may import engine/query concerns.
- `src/ta/error.rs` provides `TaError` with `TaErrorKind::{Validation, InvalidPeriod,
  NonFiniteIndicatorOutput, Computation}` and a `TaResult<T>` alias. `src/ta/mod.rs` also exposes
  `validate_finite_value`. These are the error contracts the new code must reuse.
- `src/ta/kernel.rs` defines `Kernel` with associated `Input`/`Output`/`State` types and a
  `transition()` method; `src/ta/ops/*` implement indicators strictly on this pattern. A new
  I-Ching core can follow either the same stateful-kernel shape or a set of pure functions; both
  are consistent with the module boundary (nothing in `ta` may do I/O).
- `src/model/kline.rs` defines `Kline { open, high, low, close, volume, time: i64, adjclose }`.
  `time`'s epoch unit (seconds vs. milliseconds) is **unresolved** throughout the codebase per the
  research doc §5.4 — noted as an open question, not resolved here.
- `Cargo.toml` already carries `chrono = { version = "0.4", features = ["serde"] }` and `serde`/
  `serde_json`/`reqwest` (async), giving us both a pure-algorithm path (chrono for Gregorian
  fields) and an HTTP-client path (reqwest) if an API lunar source were selected.
- `src/ext/` currently hosts `bingx`, `yfinance`, `ntfy` (feature-gated), and `webdriver`
  (feature-gated); `src/ext/mod.rs` shows the pattern for adding a new `lunar` submodule.
- No existing `src/ta/iching/` or `src/ext/lunar/` module exists; `grep` over `src/` finds no
  `iching` or `lunar` references, so this is greenfield within existing boundaries.
- The research spec (440+ lines) is treated as **normative where not overridden by the user**:
  the Xiantian trigram table (§2.2), binary-index convention (§2.1), the Gua Qi solar-longitude
  approximation and 12-sector table (§3.2), and the Fu Xi wheel quantization (§3.3) all remain
  authoritative. The user overrides three specifics: (1) lunar resolution must NOT be offline/
  fixture-based; (2) the public signal is a 7-bit `u8`, not the `IchingRecord`; (3) Plum Blossom
  is the first implementation priority.

## 3. Commentary-On-Decisions

Placed here to explain the L0 decisions the implementers must not re-litigate:
- **Pure-algorithm lunar conversion is the primary recommendation** over the API-client path. It
  is fully deterministic, requires no async runtime inside `ext`, satisfies past/future date
  support trivially, and keeps the core cold-path pure. The API-client path is a documented fallback
  with real downsides (network dependence, terms-of-service, date-range limits, error handling)
  and would need to be isolated behind a feature flag consistent with `ntfy`/`webdriver`.
- **The 7-bit signal encoding** — bits 1–6 = hexagram index (0–63); bit 0 carries moving-line
  presence/position. Two candidate encodings are proposed in L0, to be frozen in L1:
   1. **Positional:** `signal = (hexagram_index << 1) | ((moving_line - 1) & 0b111)`. When a moving
      line is present, `moving_line ∈ 1..=6` maps to `0..=5` in bits [0..2]; when absent (Gua Qi /
      Fu Xi), those bits are 0 and bit 0 is 0. This packs up to a 3-bit moving-line field and needs
      a designated "no moving line" codeword.
   2. **Flag scheme:** bit 0 = moving-line present (1) or absent (0), and the moving-line position
      is reported only through the internal `IchingRecord` (out of band); the public `u8` carries
      only hexagram bits plus a presence bit. This cannot be fully lossless from the 7-bit signal
      alone but is simpler and matches the "no moving line → bit 0 = 0" requirement exactly.
   The decision: if lossless position from the 7-bit signal is required, pick (1); if bit 0 is
   only a presence marker, pick (2). Default recommendation is **(1)**, since it preserves position
   and still yields bit 0 = 0 for the no-moving-line methods.
- **The `IchingRecord` stays internal.** It is the mutable working shape (method, moving_line,
  transformed index, etc.) for computing the signal, but the `pub fn` that consumes a datetime
  returns `u8`. Keeping the record internal preserves the richer research metadata without
  expanding the public contract.

## 4. Architecture Constraints

- `ta` must remain I/O-free: the I-Ching core in `src/ta/iching/` may import only standard Rust,
  `chrono`, `serde`, `serde_json`, and values from `model`. It must never import `engine`,
  `query`, `adapter`, or `ext`.
- `ext` must remain analysis-free: `src/ext/lunar/` may produce model-facing lunar values but must
  not compute hexagrams or import `ta`.
- Dependency direction is acyclic: `ext → model` and `ta → model` only. `lunar` results cross into
  `ta::iching` at the application/caller boundary as plain values — e.g. the caller feeds lunar
  month/day/branch outputs into the Plum Blossom casting function — preserving module independence.
- All errors flow through `TaError`/`TaResult`; non-finite numeric outputs are rejected per
  `validate_finite_value`. No panic-based, silent-default, or fixture-replay error paths.

## 5. Cross-Cutting Concerns

Merge into every downstream unit:
- **Pure & deterministic:** same (datetime, method, tz-policy) → same signal; no RNG, wall-clock,
  or ambient state.
- **No local file caching / no fixtures / no offline-only adapter.** All resolution is computation
  or live network; nothing persistent is written or read.
- **Past and future datetimes:** the pure-algorithm path is naturally arbitrary-range; the API path
  must handle both directions or reject clearly with a typed error if the provider cannot.
- **Time-zone / Zi-hour policy must be explicit and documented** (UTC vs. selected local-solar
  time, the 23:00–01:00 Zi wrap, midnight boundary) and never silently treat UTC as local.
- **Timestamp-unit note:** `Kline.time` seconds vs. milliseconds is unresolved; until resolved the
  I-Ching calculator should accept an explicit epoch-unit or use `chrono::DateTime` directly,
  leaving `Kline` untouched. Flag for root stabilization, do not resolve here.

## 6. Sequencing (directional, not dispatchable)

1. **Lunar calendar resolution (`ext::lunar`)** — decision on pure-algorithm vs. API client; in
   either case the interface exposes Gregorian → (lunar year/month/day, leap flag, options) with
   a validated branch derivation. This unblocks Plum Blossom's `SP = year_branch + month + day`.
2. **Plum Blossom core (`ta::iching::plum_blossom`)** — S1/S2 casting, upper/lower trigram via
   Xiantian modulo-8, moving line via S2 modulo-6, transformed hexagram flipping exactly that
   line, mutual/nuclear line selection. Produces the internal record and the 7-bit signal.
3. **Gua Qi Sovereigns (`ta::iching::gua_qi`)** — Julian-day, solar-longitude approximation
   (§3.2), 12-sector half-open mapping, `moving_line = None` → bit 0 = 0.
4. **Fu Xi Wheel (`ta::iching::solar_wheel`)** — 64-bin and 6-position quantization (§3.3) with the
   approved wheel-order table; geometric position is NOT a moving line; bit 0 = 0.
5. **Public signal facade** — the `u8` entry point dispatching on method and consolidating the
   7-bit encoding decision from §3.

## 7. Open Questions (escalate, do not silently resolve)

- **Signal encoding of bit 0:** finalize positional (option 1) vs. presence-flag (option 2) from
  §3 — requires the user to confirm whether position must be lossless out of the 7-bit signal.
- **Lunar source decision:** confirm pure-algorithm (recommended) vs. free-API client. If API,
   requires provider selection, availability/TOS diligence, date-range policy, and feature-gating.
- **`Kline.time` unit:** seconds vs. milliseconds remains statewide-unresolved; the calculator
  should be `Kline`-independent and take an explicit datetime to avoid coupling.
- **Plum Blossom time-zone policy:** UTC vs. local-solar-time convention and the Zi-hour rule need
  an explicit named policy before the casting adapter exists.

## 8. Escalation Boundaries & Out of Scope

- DuckDB `project()` path, virtual-table seams, and SQL projection are out of scope; DuckDB never
  computes I-Ching values.
- The record-to-aggregate scalar bridge remains intentionally unresolved (research doc §5.2) —
  blocked on root-library stabilization; do not smuggle an `IchingRecord` through the aggregate.
- L1/L2 unit decomposition, file trees, and implementation code are out of scope for this L0 and
  belong to the next planning pass.
